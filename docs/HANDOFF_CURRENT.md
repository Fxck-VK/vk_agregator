## Как объединить с работой коллеги

1. Прочитать корневой `AGENTS.md`, `.agents/state.json`, `docs/ARCHITECTURE.md`
   и инструкции затронутого пакета. Для интерфейса — `web/platform/AGENTS.md`
   и `web/platform/docs/ui-index.md`.
2. Проверить `git status`. Сначала сохранить незакоммиченную работу коллеги
   согласованным способом; не перезаписывать её загрузкой папки поверх проекта.
3. В существующем рабочем checkout выполнить `git fetch origin` и сравнить
   свою ветку с `origin/dev-deploy` через `git log --left-right --oneline HEAD...origin/dev-deploy`.
4. Если история разошлась, выполнить обычный `git merge origin/dev-deploy`
   в рабочую ветку коллеги, разрешив конфликты с сохранением обеих работ.
   Если доступен fast-forward, использовать его. Не выбирать всю сторону
   ours/theirs автоматически.
5. Проверить результат и полный состав изменений. Для подготовки нового релиза
   использовать существующий preflight из раздела ниже, а не ручной сокращённый набор.

Нужно сливать историю ветки целиком. Только два последних коммита содержат
оптимизацию релиза; шаблоны, переводы, почта и остальные возможности пришли
предыдущими коммитами. Cherry-pick только последних двух не перенесёт весь проект.
Новый push/deploy выполняется при отдельном поручении владельца.

## Где продолжать оформление и перевод

- Маршруты — `web/platform/src/app`; публичные компоненты —
  `web/platform/src/components/public`; каталог повторно используемого UI —
  `web/platform/docs/ui-index.md` и связанные разделы `ui-catalog.md`.
- Переиспользовать блок главной на другой странице только при совпадении с её
  макетом. Не добавлять универсальную шапку или подвал вопреки референсу.
- Данные текущих публичных шаблонов — `web/platform/src/i18n/public`;
  локализация — `web/platform/docs/public-template-localization.md`.
- Аудит перевода: `docs/research/ru-template-translations`, 3749 записей
  source/RU/back. Процесс: EN → RU → отдельный обратный перевод → сверка смысла.
  Сохранять ID, slugs, цены, пути и пользовательский ввод; юридические тексты
  не переводить заново. После правок выполнять `public-copy:check`.
- Будущие тысячи статей и карточек должны иметь отдельные локализованные записи
  в контентном слое `web/platform/src/content`, а не попадать целиком в общий
  клиентский словарь. Публикация в sitemap требует выполнения publication gates.
- Карта документации — `docs/INDEX.md`; исходное исследование типов —
  `docs/research/epifera-seo-structure/catalog.json`. Его ранние планы не заменяют
  текущий реализованный код и контракт локализации.
- Сохранённые HTML-референсы проверять в `references/magnific-html/` и
  `references/magnific-html-js/`. Локальные исследовательские выгрузки могут
  отсутствовать после Git fetch; для точной визуальной сверки запросить их у владельца.

повторяются только неуспешные или истёкшие этапы. Security receipts действуют 24 часа.
Новый SHA требует своей полной проверки; не переносить receipts с другой машины.
