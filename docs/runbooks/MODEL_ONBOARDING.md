# Добавление и изменение модели

Статус: действующий процесс. Применяется к новой модели, версии, провайдеру,
операции, формату вложений и изменению существующих ограничений.

## Что является контрактом

`internal/service/providermodels` остаётся реестром маршрутов. Типизированный
контракт допуска описывается пакетом `internal/service/modelcontract` и содержит:

- точные public ID, provider ID, provider model ID, версию и метод подключения;
- отпечаток соответствующей записи реестра;
- категории: `popular`, `images`, `text`, `video-audio`, `free`, `study-work`;
- операции с отдельными структурами `text`, `image`, `video`, `audio`;
- документированные возможности входов и отдельно включение их в нашем продукте;
- публичные источники документации и даты проверки;
- результаты обязательных проверок и ссылки на сохранённые отчёты.

Поддержка входа имеет три значения: `unknown`, `unsupported`, `supported`.
`enabled: true` разрешено только при `supported`, реализации обработки и успешных
актуальных проверках. `unknown` не означает, что модель умеет принимать файл.
Способ обработки документов — `native` либо `extracted_text`. Это разные сценарии:
извлечение текста не подтверждает понимание иллюстраций, таблиц или сканов.

Категории интерфейса и тип операции различаются. Модель может иметь несколько
операций и категорий. Аудиоконтракт описывает возможности, но сам по себе не
создаёт обработчик аудио или новый публичный API.

## Обязательный порядок для агента

### 1. Исследование конкретного подключения

- [ ] Установить точные модель, версию, провайдера, endpoint и метод.
- [ ] Прочитать текущую официальную документацию именно этого подключения.
      Использовать Context7 для документации доступных там SDK/API; для
      остальных — официальные страницы провайдера. Не выводить возможности
      из названия модели, рекламной карточки или другого провайдера.
- [ ] Сохранить публичные ссылки без токенов и дату фактического чтения.
- [ ] Отдельно записать неподтверждённые значения. Не угадывать лимиты и цены.
- [ ] Проверить, реализованы ли у нас необходимые загрузка, декодирование,
      извлечение текста и передача медиа провайдеру.

### 2. Описание возможностей

Заготовки: [текст](model-onboarding/text.example.json),
[изображения](model-onboarding/image.example.json),
[видео](model-onboarding/video.example.json), [аудио](model-onboarding/audio.example.json).
Это синтетические черновики: нулевые лимиты, пустые источники и отпечатки
намеренно не проходят допуск. Заполнять только проверенными данными.

| Назначение | Обязательное описание |
| --- | --- |
| Все входные медиа | Поддержка и включение; конкретные расширения и MIME; обработка; количество; размер файла; общий размер; применимые лимиты страниц, длительности и геометрии |
| Текст | Контекст и максимальный ответ; фото, видео, аудио и документы описываются независимо |
| Изображения | Допустимые сочетания соотношения сторон и разрешения; значение по умолчанию; форматы; количество результатов; маска и прозрачность; референсы |
| Видео | Допустимые сочетания длительности, разрешения, соотношения сторон, FPS и звука; вариант по умолчанию; форматы; начальный и конечный кадры: unsupported/optional/required |
| Аудио | Назначения transcribe/speech/music/transform, языки, голоса, форматы, длительность и соответствующие входы |

Операции создания, редактирования, продолжения и прочих режимов описывать
отдельно, если у них различаются ограничения. Массив вариантов содержит только
допустимые сочетания: не перемножать независимые списки без подтверждения.
Если текущий runtime разрешает независимый выбор параметров, контракт обязан
покрывать все такие сочетания. Для изображений проверяется полное произведение
качества и соотношения сторон; для видео учитываются длительности по разрешению
и звук. При более узких возможностях провайдера сначала ограничить runtime.
Для количества вложений можно указать `allowed_counts`, например `[0, 2]`,
чтобы не разрешать одно фото. Поле `required` задаёт обязательность входа.
Текущий видеомаршрутизатор принимает один обязательный видеоартефакт; контракт
с необязательным входным видео не допускается до реализации этого режима.
Для динамических режимов, которые текущая схема не выражает, сначала расширить
схему и её проверки. Не подменять неизвестный лимит числом или фиктивным значением.

### 3. Реализация и локальные проверки

- [ ] Добавить/изменить запись реестра и контракт; черновик держать в каталоге
      своей задачи, вне `onboarding/approved`.
- [ ] Подключить адаптер в worker. API, frontend и VK/Mini App не вызывают
      провайдера напрямую. Не передавать клиенту внутренние provider ID.
- [ ] Добавить pricing keys и проверку покрытия вариантов в pricingcatalog.
      Контракт не хранит отдельную копию актуальных розничных цен.
- [ ] Проверить реальный формат файла по содержимому и MIME, а не только
      расширению; ограничения размера, количества, длительности и страниц.
- [ ] Написать положительные тесты передачи каждого заявленного входа/параметра.
- [ ] Написать отрицательные тесты неподдерживаемых форматов, отсутствующих
      обязательных кадров и несовместимых сочетаний. Отказ должен происходить
      до платного submit.
- [ ] Проверить границы: минимум, максимум, шаг, ниже/выше допустимого;
      значения по умолчанию должны принадлежать разрешённым вариантам.
- [ ] Проверить жизненный цикл Job, права на вложения, нормализацию ошибок,
      таймауты, повторы, резервирование/capture/release и отсутствие двойного
      submit/списания. Использовать существующие механизмы проекта.
- [ ] Проверить совпадение каталога, отображаемых контролов, server validation
      и фактически сформированного запроса адаптера. Проверять поведение;
      тест, который лишь повторяет записанные константы, недостаточен.

### 4. Реальные проверки

Реальный тест запускается только в согласованном DEV-контуре с явно разрешённым
провайдером, набором случаев и пределом расходов. Этот процесс не даёт постоянного
разрешения на платные обращения. Использовать синтетические неперсональные файлы.

До допуска активного реестра живые случаи выполняются отдельным интеграционным
тестом адаптера/worker с явно собранными тестовыми зависимостями. Проверка обычного
запуска приложения остаётся включённой. После допуска отдельно проверить обычный
DEV-путь с feature flag; результат этого smoke дополняет отчёт.

- [ ] На каждую операцию проверить базовый результат и заявленные особенности.
- [ ] На каждый включённый формат файла проверить, что содержимое действительно
      использовано. Для фото — вопрос, ответ на который есть только на фото;
      для документа — факт только из документа; для видео/аудио — событие или
      фраза из выбранного участка. HTTP 200 сам по себе недостаточен.
- [ ] Для выходного изображения проверить декодирование, формат и размеры;
      для видео — контейнер, разрешение, длительность, FPS и звуковую дорожку;
      для аудио — декодирование, длительность и проверяемые голос/язык.
- [ ] Проверить референсы, маску, прозрачность и начальный/конечный кадры, если
      они включены. Для смысла/качества результатов сохранить честную оценку:
      один удачный ответ не доказывает универсальную точность модели.
- [ ] Для большого числа вариантов сохранить матрицу покрытия: автоматические
      проверки всех разрешённых сочетаний и выбранные реальные пограничные
      случаи. Объяснить выбор и записать непроверенные случаи.
- [ ] При отсутствии разрешения, ключей или успешного результата оставить
      `not_run`/`failed`; не заменять живую проверку моками и не включать модель.

### 5. Отчёт и допуск

Каждая операция требует сценарии `adapter`, `negative`, `boundaries`, `pricing`,
`job-lifecycle`, `catalog`, `live-output`. Каждый включённый формат дополнительно
требует `<operation>/live-input/<images|video|audio|documents>/<extension>`.

В отчёте должны быть соответствующие заголовки, например `## reply/adapter` и
`## reply/live-input/documents/.pdf`. На каждый сценарий записать: ожидаемое
поведение, способ/команду проверки, фактический результат, ограничения покрытия,
дату и проверявшего. Не хранить ключи, приватные URL, реальные пользовательские
файлы, запросы или ответы. Использовать [шаблон отчёта](model-onboarding/verification-template.md).

`checks` ссылается на относительный Markdown-файл рядом с контрактом, его SHA-256,
дату проверки и `contract_digest`. Пустые, неуспешные, устаревшие результаты,
отсутствующие/изменённые файлы и потерянные разделы не проходят допуск.
Валидатор подтверждает полноту и целостность отчёта, но не может доказать правдивость
ручного утверждения. Просмотр отчёта и фактических результатов обязателен.

```powershell
# Только чтение: точные привязки текущего реестра.
go run ./scripts/models/check -bindings

# Показывает digest, незавершённые случаи и причину отказа.
# Код 0 означает готовность контракта и совпадение с записью реестра.
go run ./scripts/models/check -contract path/to/model.json

# Проверка всего активного реестра без обращения к провайдерам.
go run ./scripts/models/check
go test ./internal/service/modelcontract ./internal/service/providermodels ./scripts/models/check
go test ./internal/service/productcatalog ./internal/platform/config
```

Проверка кандидата требует уже подготовленную запись реестра в рабочей ветке.
Пока отчёт не готов, эта ветка не проходит общий допуск. После проверки перенести
контракт и отчёты в `internal/service/providermodels/onboarding/approved`, повторить
команду для всего реестра и профильные тесты адаптера, worker и UI. Все файлы
встраиваются в сборку. `ready` не включает feature flag и не разрешает deploy.

При изменении версии, провайдера, возможностей или записи реестра digest меняется.
Повторить затронутые проверки; для остальных выполнить регрессионные проверки
и явно описать покрытие. Не переносить старые успешные отметки на новый digest
автоматическим скриптом.

## Существующие модели и границы этой доработки

`onboarding/legacy.json` фиксирует 43 существовавшие записи на момент внедрения.
В отпечатки видеомаршрутов входят также их старые provider-model алиасы.
Статус `legacy-unverified` сохраняет прежние правила доступности, не подтверждает
новые возможности и не заменяет реальные проверки. Изменение такой записи
требует контракта. Запрещено добавлять новые исключения или обновлять отпечатки,
чтобы обходить проверку; при миграции записи удалять её исключение после проверки.

Проверка исполняется в `Registry.Validate`, при проверке runtime config и сборке
product catalog, а также в CI. Её нельзя заменить отметкой в Markdown.
Поля контрактов допуска не публикуются напрямую. Сайт получает безопасную
типизированную проекцию `GET /web/v1/models`, собранную productcatalog из реестра,
доступного runtime и серверных цен. Описания, категории и параметры UI имеют
общий источник; загрузчики отдельных назначений — проекции этой выдачи.
См. [Единый каталог](../../docs/runbooks/MODEL_CATALOG.md) и
[матрицу существующих записей](model-onboarding/existing-models-2026-09-14.md).
Эта миграция не повышает `legacy-unverified` до проверенного статуса.
