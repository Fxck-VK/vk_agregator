# Website invitations

The website now uses canonical `account_id` referral codes and relations. Migration 000056 allows account-owned rows without synthetic legacy VK users and adds anonymous invitation visits. Existing account codes are reused across surfaces.

`GET /web/v1/referrals` returns the authenticated account's code and cumulative website funnel counters. Visits count saved browser invitation bindings; registrations include later activated/rewarded website relations. Legacy VK relations are excluded from these website counters. It exposes no invited-user identities or payment information.

The website caches only the validated referral code in the current tab's memory, scoped to the confirmed account and browser-session revision. Reopening the referral tab shows the link immediately and refreshes counters through authenticated `GET /web/v1/referrals/stats`, which skips code lookup/allocation. Statistics are not cached; failures show a retry while the saved link remains copyable. Logout, expiry and account changes abort the session and clear the code even while the referral tab is unmounted. Obsolete responses cannot refill the cache. A full document reload or a new tab fetches the code again. No local/session storage or server-rendered shared cache holds it; preview neither reads nor writes it. Both routes require the cookie principal and return no-store responses.

`/{locale}/invite/{code}` records an invitation through same-origin `POST /web/v1/referrals/visit`. The first invitation stays in a Secure, HttpOnly, SameSite=Lax cookie for 30 days. Only its SHA-256 hash enters PostgreSQL. Resetting cookies or using another browser can create another visit; visits are not unique people. Transient per-cookie limits run before the aggregate anonymous write limit, without storing IP addresses. Resetting cookies can evade the per-cookie limit; the shared global cap still bounds writes.

`POST /web/v1/referrals/accept` requires the cookie session and CSRF. It derives the invited account from the server principal. A transaction locks the intent and account, checks expiry, account creation time and self-invitation, then inserts at most one referral per invited account. An old account cannot become a new referral. Replays for the same account are safe; a different referrer cannot replace the first relation.

Email registration and OAuth login callbacks attempt acceptance after issuing the session. A storage outage leaves the invitation cookie intact and does not turn a successful sign-in into an error. Workspace initialization retries acceptance at most three times; another page load retries again. Terminal ineligibility clears the cookie.

The maintenance worker deletes expired visit token hashes in batches of at most 1000. The same transaction adds those visits to a per-referrer aggregate, so cumulative statistics remain stable. Accepted referral relations remain intact. Cleanup must run through a transaction-capable PostgreSQL pool; a non-transactional maintenance querier fails closed. Expired hashes can remain until the next maintenance sweep or while a backlog is being drained.

## First-payment rewards

The approved policy is `domain.CurrentWebReferralRewardPolicy`: 50 permanent stars for the inviter, once per invited new account, 24 hours after the service verifies its first successful live YooKassa payment. Any tariff or top-up qualifies; there is no limit on the number of invited paying accounts. Test/mock payments do not qualify. The registration attribution rules above are unchanged; no new reward is granted to the invitee.

Migration 000066 adds immutable payment/refund evidence and one reward record per invited account. Authenticated provider GET establishes payment mode, exact binding and amount; frontend metadata is never proof. Known test evidence is excluded from first-payment selection. Unknown mode and historical settled payments prevent a later repeat/renewal from masquerading as the first payment. Existing committed top-up ledger timestamps backfill historical evidence without retroactive awards. A settled old-writer replay cannot become a new live reward. Late invitation acceptance can discover already verified payment evidence.

Payment evidence commits with settlement. Successful refund evidence commits before the existing principal refund path, including externally refunded top-ups and partial subscription refunds which the principal path cannot automate. Any confirmed partial or full refund cancels a pending reward or reverses the full 50 stars after award. Another payment never requalifies that invitee. Pending/failed refund requests are not proof. Existing principal-refund limitations remain separate; do not infer that all external/partial principal refunds are now automated.

`MaintenanceRepository.ProcessWebReferralRewards` is the canonical bounded processor, invoked by worker cleanup and the provider-webhook's one-minute maintenance loop. Exact 24-hour eligibility is followed by the next successful sweep; outages/backlogs delay processing. Qualification, deterministic ledger keys, bonus lot and counters commit atomically. Claimed rows use SKIP LOCKED; wallet locks follow canonical owner order across batches. Multiple workers and duplicate callbacks cannot double award/revoke. The normal ordered migration must precede new application writers.

The grant is a dedicated `bonus` lot with NULL expiry. Revocation appends a full negative ledger adjustment, removes only this lot's available remainder and creates nonexpiring legacy debt for its spent/held part. Reservations remain allocated and may finish normally; a later release offsets the debt without a second expiry debit. Purchased/subscription lots retain their provenance. Balance can become negative and new credits offset it; revocation never initiates a card charge. Do not implement this with a generic FEFO debit or direct cached-balance edits.

Both authenticated summary routes return `rewards_enabled` and `reward_policy`. Activated counts first-payment qualification; rewarded counts current unrevoked awards and can decrease after refund. No invited-account identity/payment details enter responses. Preview performs no reward actions. Existing legacy VK rewards remain separate and exclude source=web.

Rollout: apply migration 000066, deploy API/worker/provider-webhook/website together, confirm maintenance health, then verify one non-test first payment and one refund in the authorized environment. Local isolated-DB evidence is not a DEV deployment or real-money validation. For rollback, retain financial evidence and migrations; 000066 down deliberately refuses destructive removal. Monitor existing maintenance errors rather than retrying manual balance changes.

Google adapters and stored bindings remain, but `ACCOUNT_OAUTH_GOOGLE_ENABLED` defaults to `false`. Stored credentials alone do not enable it. Google login/link buttons are hidden, and a disabled Google binding does not permit removal of the last working login. Profile/menu labels prefer the verified primary email. DEV rollout checks Google is disabled even if its credential overlay exists.

Before rollout, apply the normal ordered migrations and deploy API and website together. Migration rollback refuses to discard collected web invitation data; retain migration 000056 when rolling code back. Local preview performs no real referral requests and shows no invented counts.
