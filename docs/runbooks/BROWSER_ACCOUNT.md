# Browser account access

Status: implemented browser integration, 2026-10-04. Provider login and code delivery require operator configuration and real-provider smoke before enabling them for users.

The platform uses `/web/v1` cookie sessions and the shared Account Layer, rather than token-returning `/account` login routes. `GET /web/v1/auth/methods` exposes availability flags and configured provider names. Login and profile receive this contract on the server; missing configuration disables the corresponding actions.

## Sign-in completion and diagnostics

Password login and accepted email registration explicitly confirm the browser's cookie session using a no-store `GET /web/v1/me` with a 10-second deadline. The safe profile must parse successfully and match `X-NeiroHub-Account-ID` from cookie issuance when that header is present. Both cookie-changing writes use the shared cross-tab session lock and announce the account change. Confirmation does not invoke general read/refresh recovery. A verified session starts full document navigation to a validated localized `/app` return path, avoiding cached guest layouts. The form remains busy until unload; a 12-second navigation watchdog restores controls with a specific failure if the page remains. Retrying accepted sign-in only rechecks the session and navigation, without another password or registration write. Returning to sign-in allows credentials to be submitted anew.

The login form distinguishes rejected credentials, rate limiting, temporary service failure, network/timeout, DEV access expiry, rejected requests, unconfirmed/invalid sessions, account changes and failed navigation. It shows a short localized reason and error reference. Browser console event `auth_sign_in_failed` includes only `diagnostic_id`, validated UUID `request_id` (or null), enum `stage`/`code`, numeric `status` and `duration_ms`. No email, password, cookie, token, URL, response body or raw exception is logged. A local diagnostic ID for a transport failure is not evidence that a request reached the backend.

For a reported reference, correlate the UUID with the existing Next `web_proxy_failed` and Go `web_request_failed` records. Credential rejection returns 401, a rate limit 429, and storage/session availability failures 503. Safe Go stages identify `password_request`, `password_dependencies`, `password_credentials`, `password_rate_limit`, `password_authentication` (combined credential/session transaction) and `password_session_cookies`; `/me` failures use the existing profile/session stages. Confirmation can fail when cookies are blocked, stripped or expired; its message suggests checking cookies without claiming that is the proven cause. Successful responses alone do not establish working browser cookies.

Checks: `go test ./internal/adapter/inbound/websession -run TestPasswordLogin -count=1`, platform auth/session unit suites, then `npm run build` and `npm run test:sign-in-browser`. The browser fixture starts the built standalone platform against a loopback fake backend and verifies cached guest navigation, rejected cookies, service failure and correlation IDs. It copies public/static build assets like the deployed packaging, uses synthetic credentials, and never accesses real accounts or sends mail. Live DEV authentication still requires a separately authorized operator smoke.

## Email and phone

- Email/password login accepts a verified email with a password. Public registration is email → six-digit code → password → account and cookie session; `registration` in the availability contract is enabled only with configured SMTP and the registration service. An older contract without this flag keeps registration disabled.
- Registration uses `POST /web/v1/auth/email/request-code`, `/web/v1/auth/email/verify-code`, then `/web/v1/auth/email/register`. Every public mutation requires exact Origin. The server creates a Secure HttpOnly `__Host-nh-signup` cookie; its random binding must accompany code confirmation and account creation. The code and proof expire after 10 minutes. No account ID, verification assertion or proof token is accepted from browser JSON.
- Redis stores hashed email, HMAC code and one-use proof; comparison/consumption are atomic. Limits are three requests and five verification attempts per email per 15 minutes; a broad 100-request ceiling applies to the transport peer, which may be a shared BFF (not an individual user's IP). Additional account-auth limits apply at creation. Redis outages fail closed. `VK_APP_SECRET` supplies the existing server secret with a separate registration HMAC scope.
- Account, verified email, Argon2id credential and audit entries are created atomically. A proof maps to a stable server-issued account UUID so transient storage/session/cookie-preparation failures can restore that proof with its original expiry. Retrying preserves the first password; the form keeps it read-only for a transient retry and clears it when leaving or completing the flow. Existing email identities cannot be overwritten or merged through registration.
- Recovery: `POST /web/v1/auth/password/request-reset` with email, then `/web/v1/auth/password/reset` with email, code and `new_password`. Both require exact Origin. Request-code returns the same accepted response for known and unknown emails. A successful reset revokes existing account sessions.
- Recovery/link/phone/backup codes are consumed with one exact compare-and-delete operation after validating the proof. Concurrent requests have one winner; store failure cannot authorize a request. Invalid codes leave a valid challenge intact. A stale reader or failed older delivery cannot delete a replacement challenge. A failure after consumption requires a fresh code.
- PostgreSQL recovery rechecks verified email ownership under the account lock, then commits credential, revocation, audit and security notice enqueue together. An email removed/replaced between initial code validation and the transaction cannot reset the password. Login rechecks the exact validated credential and email binding under that lock before inserting its session. Session rotation shares the lock, preventing a concurrent refresh from escaping revocation. Local regressions use isolated accounts/schemas, without changing real accounts.
- A backup email is the second verified email binding on the same account. Profile labels primary/backup from server `email_role`, hides adding another address when two emails exist, and offers Replace/Unlink for the backup. Both addresses share the account password and recovery. Legacy additional addresses remain linked and may be removed; adding more is blocked.
- Backup replacement uses `POST /web/v1/account/identities/email/backup/request-code` and `/verify` with `identity_id`, `email`, then `code`. Cookie principal, exact Origin and CSRF are required. The backend captures the binding version; browser JSON cannot supply it. The current backup remains working until proof succeeds and the atomic update/audit commits. Concurrent replacements accept only one captured version. Conflict leaves the old binding and resets the UI to another address. A stale target refreshes the profile. Stable 409 errors are `email_limit_reached`, `backup_email_changed`, and `email_already_linked`.
- Recovery verifies email proof through `accountlink.VerifyEmailRecoveryCode`, without invoking identity linking, and accountauth rechecks the email's current owner before updating the password. A concurrent unlink after initial resolution must not reattach the removed address.
- Configure `ACCOUNT_EMAIL_DELIVERY_PROVIDER=smtp`, `ACCOUNT_EMAIL_SMTP_HOST`, `ACCOUNT_EMAIL_SMTP_PORT`, `ACCOUNT_EMAIL_SMTP_USERNAME`, `ACCOUNT_EMAIL_SMTP_PASSWORD`, `ACCOUNT_EMAIL_SMTP_FROM`, and existing TLS/timeout settings. Without SMTP, recovery and email linking are unavailable.
- The profile links email and phone with codes through the existing account linker. Phone is a binding, not standalone SMS login. Enable the existing HTTP delivery adapter with `ACCOUNT_PHONE_DELIVERY_PROVIDER=http` and `ACCOUNT_PHONE_HTTP_*` settings.
- Authenticated mutations require cookie principal, matching Origin and CSRF. Client account IDs cannot establish authority.
- Profile `password_set` distinguishes first setup from change; absent status disables the password action instead of guessing. `POST /web/v1/account/password/set` accepts verified `email`, new `password`, and `current_password` for an existing credential. Initial setup is insert-only; replacement verifies the current password and atomically replaces only the verified hash. Missing/stale confirmation returns 409 `password_confirmation_required`; incorrect current password returns 400 `current_password_invalid`, without ending the session. Both cases preserve the existing credential. Credential, audit, revocations and notice enqueue commit together. Browser changes preserve only the active session established by the server principal and revoke other account sessions; request JSON cannot select it. Legacy mutations without a cookie session and password recovery revoke all sessions. Concurrent legacy hash upgrades cannot overwrite a newer password. UI repeats the new password and clears password fields after submission or cancellation.

### Security notices

Migration `000055_account_security_notices` creates a private transactional outbox. Password changes/resets and backup email add/replace/remove enqueue fixed event notices for verified account emails. Removing or replacing an address includes its previously verified recipient as well as remaining/new verified addresses. Initial registration does not enqueue a backup-change notice. Each event deduplicates its recipient list. A failed database transaction leaves neither the change nor its notice committed.

When SMTP is configured, the API starts one bounded `accountnotices` loop. It leases one notice for 60 seconds, bounds SMTP to 10 seconds and each database operation to 5 seconds, and polls every 5 seconds. Delivery failure retries after 1 minute, doubling up to 1 hour. A lease token fences acknowledgements from expired workers. SMTP is outside the mutation transaction, so a delivery outage cannot turn a committed password/email change into an error. Delivery is at least once: SMTP acceptance followed by an acknowledgement failure can cause a duplicate notice.

Fixed Russian templates contain only event/time information, with no password, code, token or private link. Logs contain only notice UUID, event enum and status; never recipient, body or raw SMTP errors. Cleanup selects delivered records after 24 hours and undelivered records after 7 days, in batches of at most 1000; active leases and backlog can delay deletion. SMTP-enabled dispatch sweeps every 5 seconds; a cleanup-only loop sweeps hourly when SMTP is disabled. Outbox recipients are private delivery snapshots and must be protected with the database. Unit/integration checks use fake delivery; they do not establish inbox receipt. Apply the migration before running the updated API. If SMTP is disabled, notices remain queued until delivery is enabled or their retention expires.

### Resend sending configuration

The verified sending domain is `notify.neiirohub.ru`. Use the existing SMTP adapter; no Resend key or SDK belongs in the frontend. Configure the selected backend runtime with these non-secret values:

```dotenv
ACCOUNT_EMAIL_DELIVERY_PROVIDER=smtp
ACCOUNT_EMAIL_SMTP_HOST=smtp.resend.com
ACCOUNT_EMAIL_SMTP_PORT=587
ACCOUNT_EMAIL_SMTP_USERNAME=resend
ACCOUNT_EMAIL_SMTP_FROM=noreply@notify.neiirohub.ru
ACCOUNT_EMAIL_SMTP_TLS_MODE=starttls
ACCOUNT_EMAIL_SMTP_TIMEOUT=10s
```

Set `ACCOUNT_EMAIL_SMTP_PASSWORD` to the Resend API key in server secrets/runtime env only. Keep rotation of disclosed keys in the operator workflow. The selected API container already receives its runtime env file; restart/redeploy it after changing configuration. For DEV, the dedicated repository secret `DEV_ACCOUNT_EMAIL_SMTP_PASSWORD` is applied by `scripts/deploy/prepare-dev-email.sh` without replacing the existing split secrets. Dispatch `Deploy DEV` from `dev-deploy` to install or rotate the ignored server-only `.env.dev-email` overlay (mode 600, email settings only). It is read only by the DEV API, after the main env file, and survives subsequent automatic deployments; it is excluded from Git and Docker build context. Local runtime configuration stays in ignored `.runtime/email-registration/local.env`; set `NEIROHUB_LOCAL_WORKSPACE_PREVIEW=0` and the local backend origin in the ignored platform development env for real delivery. No mail secrets belong in that frontend env. A mailbox for this sender is not required. Receiving and click/open tracking are unnecessary for verification codes.

For delivery smoke, use an explicitly provided recipient and the selected contour. Request a code once, check the recipient inbox and Resend delivery status, confirm it in the same browser, set a password, and verify login/logout with the new account. Mock delivery and local preview do not establish real delivery. [Resend SMTP documentation](https://resend.com/docs/send-with-smtp).

## External login

Register the exact HTTPS callback `${WEB_ORIGIN}/web/v1/auth/oauth/{provider}/callback` (`google`, `apple`, `vk`, `telegram`). WEB_ORIGIN is the public frontend origin. The first client ID in each existing audience list is the browser client; mobile IDs follow it.

| Provider | Browser configuration | Proof |
| --- | --- | --- |
| Google | `ACCOUNT_OAUTH_GOOGLE_CLIENT_IDS`, `ACCOUNT_WEB_OAUTH_GOOGLE_CLIENT_SECRET` | code + PKCE, verified OIDC token and nonce |
| Apple | `ACCOUNT_OAUTH_APPLE_CLIENT_IDS`, `ACCOUNT_WEB_OAUTH_APPLE_CLIENT_SECRET` | code, verified OIDC token and nonce |
| VK ID | `ACCOUNT_OAUTH_VK_ID_CLIENT_IDS` | code + PKCE + state, server-side user_info |
| Telegram | `ACCOUNT_OAUTH_TELEGRAM_CLIENT_IDS`, `ACCOUNT_WEB_OAUTH_TELEGRAM_CLIENT_SECRET` | code + PKCE, verified OIDC token and nonce |

For DEV Google, create a Google OAuth client of type Web application with the exact callback `https://dev-web.neiirohub.ru/web/v1/auth/oauth/google/callback`. Store its client ID in the dedicated repository secret `DEV_ACCOUNT_OAUTH_GOOGLE_CLIENT_IDS` and its client secret in `DEV_ACCOUNT_WEB_OAUTH_GOOGLE_CLIENT_SECRET`. Keep downloaded credentials outside Git. Both dedicated secrets are required together; missing both preserves existing configuration, while a partial or malformed configuration stops deployment. The first dedicated client ID is the browser client; existing mobile audiences are retained and deduplicated. `scripts/deploy/prepare-dev-google.sh` renders only the two Google settings to the server-only `.env.dev-google` overlay, mode 600, read by the DEV API after its base env and email overlay. Manual `Deploy DEV` applies the settings; the overlay persists through subsequent automatic deployments. The overlay is ignored by Git and Docker build context. Do not reuse this DEV client or copy its secrets into production. Ordinary HTTP localhost remains unavailable for OAuth in the current backend, which requires an HTTPS web origin; local OAuth needs a separately registered HTTPS callback.

Secrets belong in deployment secrets/runtime env, never NEXT_PUBLIC variables. Apple's secret is an operator-generated, signed client-secret JWT; renew before expiry. Apple uses code-only response_mode=query without name/email scopes. Telegram uses OIDC client credentials, not the legacy Login Widget bot token. Existing issuer/JWKS configuration still applies to OIDC verification.

Login starts at `POST /web/v1/auth/oauth/{provider}/start`; profile linking starts at `/web/v1/account/oauth/{provider}/start`. They return the authorization URL. Server-owned Redis transactions expire after 10 minutes and bind provider, browser cookie, state, PKCE, nonce, locale and optional owning account. Consumption is atomic and one-use. Linking must have a valid session for the same account at completion; conflicts do not merge accounts.

Provider tokens stay on the backend. Login issues existing Secure HttpOnly cookies. The frontend proxy permits only fixed 303 callback destinations, preserves separate Set-Cookie headers and sets Referrer-Policy=no-referrer. JWKS cache entries are bound to their source URL.

## Profile and preview

Profile → Access and security shows bindings, code verification, password setup and active sessions. Revocation is owner-scoped. Ending the current session uses the shared cookie logout under the refresh lock, clears client account state and returns to login. Device/IP/token hashes are not displayed. Both shared identity repositories preserve a verified non-phone sign-in method when unlinking; PostgreSQL serializes unlink operations with an account row lock before counting identities inside a transaction.

`npm run dev:preview` shows all future provider buttons disabled. Recovery and registration are marked local UI simulations: they never send mail, create accounts or change passwords. Registration accepts any six-digit preview code and explicitly labels both code/password steps as simulation. Profile mutations are disabled. The preview route continues to block writes to a real backend; preview is development-only.

## Verification and release

Backup email coverage: `go test ./internal/adapter/inbound/account -run 'TestBrowser(Backup|Unconfirmed|Removed)' -count=1`. These browser-boundary tests cover code-confirmed linking, the same account after recovery, shared password replacement, old access/refresh token revocation, used-code rejection, unconfirmed/conflicting/removed addresses. Fake email delivery is used; this does not establish real inbox delivery. For an authorized live smoke, add a distinct address in Profile → Access and security, confirm its code, then use that address under “Forgot password?” and sign in with the new password. This intentionally changes the account's password and ends its old sessions.

Tests cover Origin/CSRF, anti-enumeration, reset revocation, provider exchange, PKCE/nonce, browser binding, expiry/replay, signup throttling, concurrent duplicate creation, atomic rollback, session/cookie retry, session ownership, callback redirects and preview isolation. Run focused Go tests, platform auth/account/proxy tests, lint, typecheck and build.

Before enabling real methods, configure the provider and delivery channel, register callbacks, complete login/cancel/link/conflict with operator test accounts, verify real delivery/registration/recovery, and verify session revocation. These external operations are not established by unit tests. Isolated PostgreSQL tests require TEST_DATABASE_URL; the registration Redis integration test requires TEST_REDIS_URL. On 2026-10-04 these ran against local PostgreSQL 16 and Redis 7, including concurrent registration, rollback and credential preservation. Real Resend SMTP authentication and the local browser request-code step also passed with an operator-authorized recipient. Inbox receipt and account creation require the operator's code/password steps; SMTP acceptance alone does not establish inbox delivery. A sending-only Resend key cannot read delivery status through the email-list API.
