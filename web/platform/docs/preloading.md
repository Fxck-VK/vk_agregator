# Загрузка рабочей области

Статус: реализовано локально; восстановление чтений и сессий обновлено 29 сентября 2026. Публикация этих изменений отдельно. Визуальное согласование отдельных состояний продолжается по общему списку.

Цель: рабочий экран сохраняет геометрию и доступные действия при медленной сети;
задержка одного ресурса не скрывает остальные, обновление не уничтожает данные и черновик.

## Границы

- Каркас с навигацией отрисовывается через Suspense до проверки сессии. Приватные
  данные и действия появляются только после серверной проверки личности.
- Проверка `/me` не ожидает баланс и список диалогов. Эти ресурсы независимы,
  имеют собственный повтор и не подменяют ошибку нулевым балансом/пустым списком.
- Сервер заранее запрашивает каталог. Нормализованный каталог не содержит
  пользовательских данных: backend listModels не использует principal. Только
  этот ресурс допускает короткий серверный кеш; проверка сессии остаётся обязательной.
  Медленный холодный каталог не блокирует всю страницу: ожидание начального
  снимка ограничено, после него работает общий клиентский загрузчик.
- Общий клиентский каталог получает серверный снимок и обновляется в фоне.
  Запросы объединяются, ошибка обновления сохраняет ранее показанные модели.
  Оплата, доступность модели и приём задания остаются ответственностью backend.
- Приватный кеш историй и файлов принадлежит экземпляру рабочей области конкретного
  аккаунта и остаётся в памяти. Отдельное исключение — последние 20 записей списка
  чатов: id, заголовок до 240 символов, created_at/updated_at. Они сохраняются
  максимум на сутки в localStorage только после серверной проверки аккаунта,
  очищаются при выходе/смене аккаунта и подтверждённом окончании сессии. Тексты
  сообщений, вложения, токены и другие поля туда не записываются. Это снимок для
  отображения, не источник полномочий; backend проверяет каждое действие.
- История и файловые карточки используют имеющийся кеш; фоновые ответы не
  перемонтируют composer и не стирают текст/локальные вложения.
- Списки используют небольшие авторизованные превью; оригинал нужен при открытии
  фото. Видимые элементы приоритетны, остальные используют lazy loading.
- Фоновое обновление списка чатов не показывает технических надписей: доступные
  строки остаются на месте. Холодная загрузка использует Skeleton; при отсутствии
  снимка и сбое появляется отдельный StateNotice с повтором. Отмена не считается
  сетевым сбоем. Записи и платные действия автоматически не повторяются.

## Проверка

Холодный вход и переходы с кешем; задержки каталога/истории/баланса по отдельности;
обрыв сети и ручной повтор; сохранение черновика и вложений при обновлении;
разделение аккаунтов; серверный HTML с выбранной моделью; размер превью,
отсутствие загрузки невидимых оригиналов; RU/EN, узкий экран, reduced motion.

## Реализация

- `WorkspaceSessionContent` за Suspense проверяет `/me`; при недоступности остаются навигация и повтор. Server catalog seed ожидается максимум 200 мс. Валидный неперсональный каталог кешируется 60 секунд; ошибки и авторизация не кешируются. Каталог по-прежнему требует авторизации backend.
- `GenerationCatalogProvider` соединяет верхний селектор, селектор чата, новую форму, каталог и блоки моделей на главной. Пока есть снимок, обновление не возвращает их в начальную загрузку. Проверка свежести — при фокусе/восстановлении сети и раз в минуту на видимой вкладке.
- Каталог сохраняет тип отказа для общего механизма восстановления: сетевой сбой/503 допускает фоновый повтор, 403 и неверный формат ответа — нет. Ошибки отдельных категорий не стирают успешно загруженные модели.
- `createReadResource` объединяет чтения и сохраняет последний успешный результат. `useReadResource` обслуживает приватные баланс и список чатов в экземпляре аккаунта. Обновление серверной сессии (включая существующий refresh после оплаты/изменения чата) инвалидирует эти чтения. Устаревший ответ не перезаписывает более новый.
- Метаданные читаются с отменой: backend ограничивает небольшие чтения/refresh 8 секундами, BFF GET/HEAD — 12, браузер — 15. Это начальные защитные бюджеты, не измеренный SLO; их пересмотр требует DEV-метрик. Записи не повторяются автоматически. Shared LoadFeedback остаётся доступен другим поверхностям; sidebar его не использует. MediaImage поясняет ожидание фото после 8 секунд, не объявляя медленную загрузку ошибкой.

## Восстановление сессии и чтений

- Browser GET/HEAD при account 401 один раз вызывает общий refresh и повторяет
  чтение. POST/PUT/PATCH/DELETE не переигрываются. SessionRefresh использует тот
  же координатор. До refresh под блокировкой повторно проверяется /me: другая
  вкладка могла уже обновить cookie. Web Locks или атомарная IndexedDB lease
  координирует вкладки; при недоступности обоих механизмов восстановление
  завершается ошибкой без небезопасной конкурентной ротации.
- Backend заменяет сессию атомарно: отзыв старой и создание новой — одна операция
  хранилища. Ошибка записи сохраняет старую сессию; конкурентная ротация имеет
  одного победителя. Отзыв/истечение возвращают 401, инфраструктурный сбой — 503.
- Password login и logout используют ту же межвкладочную блокировку. Login имеет
  общий 15-секундный бюджет ожидания/запроса, меньше срока IndexedDB lease.
  Завершение сессии/смена
  аккаунта инвалидируют старые ответы; account header сервера дополнительно
  защищает от смешивания ответов после смены общей cookie в другой вкладке.
  Успешный login уведомляет остальные вкладки; рабочая область восстанавливается
  только после нового серверного подтверждения, включая вход в тот же аккаунт.
- ReadError различает network/timeout/session/dev_access/forbidden/rate_limit/
  unavailable/invalid_request/invalid_payload/cancelled. Временные отказы чтений
  повторяются через 2/5/15/30/60 секунд с jitter; Retry-After соблюдается.
  Hidden/offline вкладка не отправляет фоновые чтения. Focus/online/visibility и
  минутная проверка на активном экране возобновляют допустимые чтения.
- DEV gate остаётся отдельным слоем. Фоновый 401 несёт
  X-NeiroHub-Dev-Access: required, без WWW-Authenticate; один переход документа
  ведёт на gateway login. Account refresh не пытается исправить DEV gate.
- BFF генерирует X-Request-ID, передаёт его Go API и возвращает браузеру.
  Диагностика содержит только request_id, status, stage, duration_ms; без URL,
  query, cookie, тела запроса/ответа, SQL ошибок и личных данных.

Проверка реального браузера: `npm run test:session-browser` поднимает loopback
фикстуру с синтетической сессией и проверяет две вкладки с Web Locks и IndexedDB.
Проверки не обращаются к живым аккаунтам, генерациям или оплатам.
- История резервирует место и оставляет редактируемый composer во время первой загрузки. До готовности данных отправка недоступна. Новая история обновляет сообщения без перемонтирования поля ввода. Текст и File/blob-вложения очищаются после принятия сообщения, сохраняются при неудаче.
- Кеш аккаунта ограничен 8 историями по 100 сообщений, первой страницей файлов и 60 результатами. «Мои файлы» и окно выбора вложений используют общий кеш метаданных. Карточки запрашивают результат при приближении к области просмотра; очередь допускает два одновременных запроса.
- `?preview=1` у внутреннего image-artifact URL получает маленький WebP (до 640×640, с сохранением пропорций). Обычная проверка владельца выполняется перед обработкой. При редиректе используется только адрес, проверенный существующим proxy; куки в object storage не пересылаются. Лимиты: 20 МиБ, 40 млн пикселей, 4 обработки, очередь до 32; ожидание очереди отменяется вместе с клиентом. Сервер не кеширует приватные байты, ответ private/no-store. Просмотрщик, скачивание и редактирование используют оригинал.
- Безопасный ImageJob DTO дополнен необязательными `aspect_ratio` и `output_count`. Они задают геометрию карточки до метаданных; старые задания без размеров используют прежний резерв 3:4 до получения результата. Worker/provider-поля остаются приватными.

Черновики и выбранные файлы хранятся в памяти открытой формы. Полная перезагрузка браузера не восстанавливает File-объекты. Нет фоновой очереди платных отправок после восстановления сети.

### Обложки видеопримеров

Видеокарточки сначала показывают отдельный WebP из первого кадра (текущие обложки
800×450 / 598×800, около 20 / 50 КБ). MP4 подключается при появлении карточки в
области просмотра; до загрузки обложки preload=none. Обложка остаётся при медленной
сети и ошибке, а при готовности первого кадра заменяется видео в тех же пропорциях.
Миниатюры большого просмотра запрашивают только картинки. Основной просмотр
подключает видео сразу и сохраняет controls, autoplay muted и ручной повтор.
Обложки подготовлены из локальных публичных MP4 заранее, без транскодирования
на сервере и без скачивания ролика ради обложки в клиентском приложении.
Это контракт видеопримеров; приватные результаты без poster не получают выдуманных
обложек. Новые видеопримеры должны включать posterPath и соответствующий asset.

## Проверки реализации

- Unit: серверный seed и ограничение ожидания, общий запрос нескольких потребителей, сохранение данных при ошибке, независимость баланса/навигации, обновление после refresh и смена аккаунта, сохранение composer, отмена старого чтения, авторизованные уменьшенные фото.
- Browser: серверный HTML без JavaScript; задержанная история → ошибка → повтор с сохранением текста; кеш файлов при отказе обновления; offline с локальным фото. Регрессии: 1–5 изображений в чате, мобильный экран, просмотрщик и 404 с работающей навигацией.
- На локальном образце PNG 1024×1536: оригинал 2 358 724 байта, превью WebP 427×640 — 24 976 байт. Это измерение одного образца, не обещание одинакового коэффициента сжатия для всех файлов.
- Реальные генерации, списания, оплаты и публикация не запускались. Проверки используют локальные фикстуры/симуляцию сети.
